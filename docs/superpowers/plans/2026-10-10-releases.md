# Automatic Releases and Version Modal Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Make each successful main push publish a versioned GitHub release automatically, and expose installed/latest version information in the CLI and a centered shell modal.

**Architecture:** Testable Python helpers classify pushes and coordinate immutable tags, GitHub releases, and version-only main updates. A shared Rust version client feeds `info --check-update` and pure modal state; the shell owns the asynchronous task and terminal drawing. Keep this as one delivery because the modal consumes the release channel established here.

**Tech Stack:** Rust edition 2024, clap 4, ratatui 0.30, Tokio 1, reqwest 0.13, semver 1; Python standard library compatible with Python 3.9+; GitHub Actions and REST API.

**Spec:** [Approved design](../specs/2026-10-10-releases-design.md).

## Global Constraints

- The initial baseline is the existing CLI version, `0.47.2`.
- Major remains zero. Minor takes precedence over patch.
- Only the CLI package version and its matching lockfile package entry are updated.
- Existing tags are never moved. Never force-push.
- `h -v`, `h -V`, and `h --version` print the same existing version line.
- The public version request has a five-second total timeout.
- `--offline` performs no request, including when retry is used.
- Use existing semantic colors, one-handed motions, and `render::print` / `render::note` for command output.
- Keep the API crate independent and unchanged; domain and drawing remain free of I/O.
- Use the existing `feat/releases` worktree. Do not manually bump Cargo versions during this implementation.
- Follow red/green TDD. Run the named tests before implementing each behavior and retain the observed failure.
- Update the named docs with the owning task. Do not change generated skills directories.

## Review Focus

1. Main advances during publication: tag the original source and preserve newer main changes (Task 2).
2. GitHub accepts a write but its response is lost: retry the existing tag/release without allocating another version (Task 2).
3. An older workflow starts late or is retried after a newer release: do not deadlock or make stale code latest (Tasks 2 and 3).
4. Installed `0.9.0` versus published `0.10.0`, prereleases, and build metadata: compare semantic precedence rather than strings (Task 4).
5. Closing and reopening during a slow request: no frozen input, duplicate requests, or stale modal result (Task 6).

**Interfaces:**
- Frozen `Push(before: str, source: str, run_id: int)` and `ReleaseRecord(version: str, before: str, source: str, commit: str, run_id: int)` live in `repository.py`.
- `Repository(path: Path)` exposes `messages(push: Push) -> list[str]`, `records() -> list[ReleaseRecord]`, `prepare(push: Push, version: str) -> ReleaseRecord`, `push_tag(record: ReleaseRecord) -> None`, and `sync_main(record: ReleaseRecord) -> None`.

- `publish_push(repository: Repository, github: GitHub, push: Push, verify: Callable[[ReleaseRecord], None]) -> Optional[ReleaseRecord]` returns `None` only for an overtaken, unreserved old source, with an explicit diagnostic. The verify callback runs against the prepared checkout before tag creation.

  `created_tags` is the fake's list of release tag names accepted on creation;
  the fixture resolves `release_commit_parent` and `main_unrelated_file` with Git.
  Also test commit subjects containing quotes, newlines, and shell metacharacters
  remain text; no shell evaluation is used.

- [x] **Observe red.** Run `python3 -B -m unittest discover -s scripts/release/tests -p test_repository.py -v` and the same command with `-p test_publish.py`; expect missing publication code.
- [x] **Implement repository operations.** Use argument arrays with `subprocess.run`, strict SHA validation, and complete `before..source` history. Reject non-ancestor ranges and sources absent from main history. Store a JSON object containing schema version 1 plus the record fields other than `commit` in the annotated tag; derive `commit` from the peeled tag. Verify its parent, version files, and version-only diff on reuse. Identify generated commits from verified release metadata and version-only contents, not merely a user-controlled subject prefix.
- [x] **Implement publication/recovery.** Fetch tags inside the publication lock. Reuse the push's reservation or increment the highest valid ledger version from the bootstrap baseline. ### Task 4: Shared semantic version reports and the GitHub client

`tests/version_check.rs`; modify `src/lib.rs`, `Cargo.toml`, `Cargo.lock`,

**Interfaces:**

- Pure `compare_versions(installed: &str, latest_tag: &str) -> anyhow::Result<VersionReport>` and `VersionReport::offline(installed: &str) -> Self` / `unavailable(installed: &str, reason: &str) -> Self`.
- `GitHubClient::new(endpoint: &str, timeout: Duration) -> anyhow::Result<Self>`; `async fn check(&self, installed: &str, offline: bool) -> VersionReport`.
- Public `async fn check(offline: bool) -> VersionReport` builds the fixed production client and uses `env!("CARGO_PKG_VERSION")`; caller configuration cannot redirect the endpoint.

- [x] **Write comparison tests.** Assert `0.9.0` versus `v0.10.0` is `UpdateAvailable`, equal versions are `UpToDate`, `0.48.0-rc.1` is older than `0.48.0`, differing build metadata compares equal, and an installed higher version is `Ahead`. Reject malformed tags and accept a future `v1.0.0` response.

Bound test timeouts tightly via the injected client timeout.
- [x] **Observe transport red.** Run `cargo test --test version_check`; require the request/status behavior to fail before implementing it.
- [x] **Implement the client.** Promote reqwest from dev-only to a direct dependency using `default-features = false` and `json`, `rustls`, `webpki-roots` features. Use the fixed public latest-release URL, User-Agent `huckleberry-cli/<installed-version>`, GitHub JSON Accept header, and five-second total timeout. Map 404 to `NoRelease`, other HTTP/network/parse failures to a concise `Unavailable` report; validate that a returned release is neither draft nor prerelease. Short-circuit offline before building/sending a request. Do not return arbitrary response bodies as UI copy.
